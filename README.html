Databricks Cluster Log Analyzer

Point it at the logs Databricks delivers for a cluster. It shows what ran, where the time went, what failed and why, which tables cost the most, how many rows moved between steps, and what to change. It runs on your laptop: no Spark, no cluster.

Why use it

It is not a perfect tool, but it is a fast one, and it helps every time. In most cases (somewhere between 90% and 99%, depending on the problem) it names the real issue on its own, in minutes and without much effort from you. When it can't name it, it still gives you more than enough data to work it out yourself: its findings help you rule things out and point you to where to dive in. So it helps with the analysis 100% of the time. As a developer you know where to look and what to fix, in minutes rather than hours, and you can trust what you find.

  • Driver, executor and Spark event logs
  • Local folder, Unity Catalog volume, ADLS, S3
  • Parquet datasets + DuckDB
  • Local web UI
  • Python 3.11+, no Node.js

What it does

It reads the raw logs (log4j driver logs, stdout/stderr, executor logs and the Spark event log), turns them into Parquet datasets, and serves a web UI on your machine. You drill down level by level, from what happened to the exact stage or task:

cluster → run (a Databricks job run, notebook or session) → query → Spark job → stage → task.

  • Time: the cluster's time on the clock next to run time added up over all runs (overlapping runs add up to more than the clock), and the time spent waiting for a free core. Each run's and each query's time is split by cause: waiting for cores, CPU, storage, GC, writing shuffle, waiting for shuffle data, or no Spark work.
  • Failures: a cluster shows as failed only when a job or query failed. Task retries that succeeded are shown as such, never as failures. It also lists lost, killed or out-of-memory executors and errors grouped by fingerprint, each with the first frame of your own code.
  • What to change: fixes grouped by impact, each with what the data shows, the likely cause and the setting or code change, plus the problems found behind it. This is shown for the whole cluster and for each run.
  • Tables: for the cluster, a run or one query: size, file count, file size, files skipped, bytes and rows pulled, scan time and task time. It flags tables with files over 1 GB, big tables read whole, and tables scanned again and again.
  • Rows: rows read and written (inserted, updated, deleted, copied unchanged) per table and query. For every stage it shows rows in, per parent stage, and rows out, and flags a join that puts out more rows than came in. It also shows the rows passed between jobs and between queries.

Install and run

Only Python 3.11+ is needed. The web UI is already built and ships in the package.

Windows (PowerShell)

git clone https://github.com/darshanmeel/databricks-log-analyzer.git
cd databricks-log-analyzer
python -m pip install -e .
dbx-log-analyzer ui --output C:\dbx\output --cache C:\dbx\cache

macOS / Linux

git clone https://github.com/darshanmeel/databricks-log-analyzer.git
cd databricks-log-analyzer
python3 -m pip install -e .
dbx-log-analyzer ui --output ~/dbx/output --cache ~/dbx/cache

Without installing the package

Install the libraries once, then point Python at src each time:

python -m pip install pandas pyarrow duckdb click fastapi uvicorn   # once
$env:PYTHONPATH = "src"                                            # PowerShell; bash: PYTHONPATH=src python3 ...
python -m databricks_cluster_log_analyzer ui --output C:\dbx\output --cache C:\dbx\cache

Cloud sources need their extra: pip install -e ".[databricks]" (Unity Catalog volumes), ".[adls]", ".[s3]" or ".[all]". To update: git pull, then restart the UI. Analyses you already have still open, and Analyze again rebuilds one with the newest findings.

  • Port in use: add --port 8766.
  • "Command not found": use python -m databricks_cluster_log_analyzer ui ....
  • Keep output and cache outside the repo: then nothing from a real cluster can be committed by accident.

Try the demo cluster

python scripts/make_demo_cluster.py ./demo_logs
dbx-log-analyzer ui --output ./demo_out --cache ./demo_cache

On Home pick Local folder, enter ./demo_logs and analyze 0112-020000-demo0001. The demo runs 5 Databricks job runs on 8 executors with 4 cores each:

  • load_customers (twice) and load_orders.
  • build_order_line_item: joins orders with customer into a staging table, then MERGEs it into order_line_item.
  • daily_revenue.

The runs overlap, so some wait for cores. One join is skewed, grows its rows ×2 and spills. One task fails and is retried. order_line_item has files of 1.5 GB and is read whole.

Home and Analyze again

  • Four steps: where the logs are (local, volume, ADLS, S3), then the root path, then the cluster (it lists them with their last change), then Analyze. Remote logs are copied to a local cache incrementally.
  • Analyzed clusters: each row shows the status and why: "2 jobs failed", or "after 3 task retries" when it succeeded anyway. It also shows the jobs failed, the task attempts retried and the findings.
  • Analyze again: rebuilds a cluster from the raw logs it was built from, with the newest version of the tool. The button is greyed out, with "Raw logs gone", when those logs are no longer on disk.

Cluster overview

  • Clock time: how long the cluster was up (1h 16m) next to the run time added up over runs (46m 34s) and how many runs were going at once on average. It prevents the "8 days of run time on a 12-hour cluster" confusion.
  • Waiting for cores: added up over runs and as a share of run time, plus on the clock: how long at least one run was waiting.
  • Where the time went and How the runs ended: the two answers in plain words, with links to the detail.
  • Where the runs' time went: one bar split by cause, then every run with its wait and run time, its usual time, rows and flags (spill, big task reads, retries). The left rail lists the runs grouped by program, worst first.

What to change

  • Highest impact first. FIX means the data is clear; CHECK means look before you change. The setting it is about (for example spark.sql.shuffle.partitions) is shown next to the title.
  • Opened: what we saw (the headline, then more facts and the likely cause on demand), the fix, links to the queries, runs and stages, and the problems found behind it. Long stage lists show the top 10 first.
  • Further down: other problems not covered by a change, by kind, and the cluster's settings with where each value came from (cluster, code or default).

Tables read

  • The headline: how many tables, the bytes and rows pulled from files, the task time, and the costliest table with its share of the time.
  • Flags: files over 1 GB (a MERGE rewrites whole files), a big table read whole with no files skipped, a table that isn't partitioned, and a table scanned several times in one run or query.
  • The list: top 10 first. Columns: size, files, per file, scans, runs, files skipped, pulled from the files (only the columns needed: Parquet is columnar), rows read, scan time and task time. The same panel is on every run and every query.

One run

  • Tiles: duration against its usual time, queries and jobs, tasks and retries, spill, shuffle, other runs on the same executors, and executors lost.
  • Cause cards name the query that did most of the work and what it read, spilled and wrote. The fixes come in the order to make them.
  • On its clock: waited for cores, ran tasks, and no Spark work (driver code). An idle gap of 30 minutes or more is called idle, not driver code. Every query is listed with its wait, run time and rows in.
  • What to change for this run: the same folded cards as the cluster, limited to the changes this run is part of, with this run's problems behind each. The full list of problems stays under Details.

One query

  • Reads and writes: every table, with the bytes read and the stages that read it.
  • Step by step: each stage with its tasks, when it was submitted, when its first task started, the wait for cores and the run time. Rows in → out shows, for example, "96.0M read → 96.0M to the shuffle" or "109M from stage 6, 7 → 214M written". You can follow the data through the query.
  • Why it took that long: the stages that held it up, with their tail, skew, spill, wait and share of the executors.
  • The graph (Flow or Time) draws the query box with its jobs and stages. Each stage box shows its rows in → out and its spill and shuffle. Each link is labelled with the rows passed over it.

One stage: rows in and out

  • Rows in: rows read from each table, plus the rows each parent stage wrote to the shuffle. A parent that Spark skipped (adaptive query execution reused its output) is marked as such. When there are several parents, the total read from the shuffle is shown too.
  • Rows out: to the shuffle for the next stage, or written to the table.
  • Flags: ×1.5 or more rows out than in means a join matched many rows per key (duplicate keys on both sides) or is a cross join. Far fewer out than in means the stage filtered or aggregated. When Spark recorded no row counts, the strip says so; nothing is guessed.

Chain of queries

Switch from Query with its jobs to Chain of queries to see every query linked to this one, upstream and downstream. A query is linked when it wrote a table this one reads, reused its shuffle output, or ran inside it. Arrows carry the rows passed. A "+" on either side unfolds the rest of the chain.

Timeline

  • Each small block is one task. Red blocks failed. A lane that ends in a red line lost its executor. Hatched stretches mean an executor was up but idle (paid for, running no task).
  • Click an incident to zoom to it, drag to zoom into a range, and click a task to open its stage.

Executors

Findings and errors

Kinds include disk spill, skewed tasks, MERGE reading far more of the target than it merged, waiting for cores, too few or too many shuffle partitions, file-reading tasks above the split size, GC pressure, out-of-memory or lost executors, and executors paid for but idle. Errors groups exceptions from the logs by fingerprint, with the first frame of your own code and the run it came from.

A 2 a.m. workflow

  1. Analyze the cluster (or click Analyze again). Read the status line: did a job or query fail, or did it only retry tasks?
  2. Cluster overview: look at clock time against time added up, waiting for cores, and the two short answers. This is where most runs show whether the issue is capacity (waiting) or the work itself.
  3. Tables read: one look tells you whether a table was read whole, has huge files, or was scanned too often.
  4. What to change: open the top card. Its problems link straight to the query or stage.
  5. Open the worst run, then its slowest query: follow the rows in → out stage by stage. A join that grows rows, a skewed stage or a spill stands out.
  6. Still not clear? The timeline, executors, errors and the raw datasets (Data / Debug) are all there to dig into yourself. Even then, the findings above have already ruled most things out.

What it cannot tell

  • Only what Spark logged. It can't see code that never reached Spark (pure Python on the driver shows only as "no Spark work"). It also can't see why a Databricks job was cancelled outside Spark.
  • Row counts are missing when Spark recorded none, for example for some scans, or for stages skipped under adaptive query execution. It then says "not recorded" and never guesses.
  • Table sizes come from scans that skipped nothing. A table only ever read with filters shows the size of what was read.
  • Serverless compute delivers no cluster logs. The analysis then says so.

Command line

# which clusters are there (newest driver activity first)?
dbx-log-analyzer clusters --root ./my-logs
dbx-log-analyzer clusters --source volume --root /Volumes/cat/sch/vol/cluster_logs --profile DEFAULT

# download (remote, incremental) and parse into <output>/<cluster_id>/
dbx-log-analyzer analyze --source s3 --root s3://my-bucket/cluster-logs --cluster 0101-000000-abcd1234
dbx-log-analyzer analyze --source s3 --root s3://my-bucket/cluster-logs --latest 5

# parse a local folder
dbx-log-analyzer build --input ./cache/0101-000000-abcd1234 [--output ./output] [--duckdb]

# older outputs: add newer findings from their datasets, without the raw logs
dbx-log-analyzer refresh-findings --output ./output [--cluster <id>]

dbx-log-analyzer ui                       # http://127.0.0.1:8765

Datasets

Each dataset is written to <output>/<cluster_id>/<name>.parquet with an explicit schema, so empty datasets keep their columns. Next to them, summary.json holds the counts, totals, cluster info, findings by severity, a plain-English diagnosis, and the folder the raw logs were read from (which Analyze again uses). schemas.py lists every column. --duckdb also loads them into insights.duckdb.

Rules and thresholds

The thresholds (skew, spill, GC, tiny tasks, shuffle-heavy), the log signal patterns, the executor removal categories and the framework stack-frame prefixes are all in one file: src/databricks_cluster_log_analyzer/rules.toml. Override them with --rules my_rules.toml or DBX_LOG_ANALYZER_RULES=my_rules.toml; your file is merged over the defaults.

Privacy

Everything runs on your machine. The web server listens on 127.0.0.1 only, and nothing is sent anywhere. Keep --output and --cache outside the repo so that logs from a real cluster can't be committed by accident.

How it is built

  • Parsing streams: files are read line by line (gzip detected by magic bytes), and event-log lines are filtered by event name before json.loads. Transforms use pandas, and DuckDB serves the UI's queries.
  • The API is FastAPI and the UI is React + Vite (frontend/). The built UI ships in src/databricks_cluster_log_analyzer/api/static, so Node.js is needed only to change it: cd frontend && npm ci && npm run build.
  • Sources implement a small interface (list_clusters, list_files, open), shared by the CLI and the API.
